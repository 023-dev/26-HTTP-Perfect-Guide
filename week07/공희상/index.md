# 캐시

복수의 클라이언트가 자주 쓰이는 원 서버 페이지에 접근 할 때,
서버는 같은 문서를 각자에게 똑같이 줄 텐데,
이렇게 불필요한 데이터 전송은 값비싼 네트워크 대역폭을 잡아먹고,
웹 서버에 부하를 준다.

캐시를 이용하면, 첫 번째 서버 응답은 캐시에 보관되고, 
뒤이은 요청들에 대한 응답으로 사용될 수 있기에
중복해서 트래픽을 주고 받는 낭비가 줄어들게 된다.

## 대역폭 병목

캐시는 네트워크 병목을 줄여준다.
대역폭은 네트워크 속도와 문서 크기에 따라 전송 시간에 영향을 준다.
개역폭은 큰 문서에 대해 현저한 지연을 일으키며,
속도는 네트워크 종류의 차이에 따라 극적으로 달라진다.

## 갑작스런 요청 쇄도(Flash Crowds)

갑작스러운 트래픽이 발생할 때 네트워크와 서버에 심각한 장애를 야기시킨다.

## 거리로 인한 지연

거리가 멀수록 서버로 부터 응답받는 지연시간이 늘어난다.

## 적중과 부적중

캐시는 유용하지만, 모든 문서의 사본을 저장하지는 않는다.(cache hit/miss)

### 재검사

캐시된 사본이 신선한지 검사해야 한다. 이를 HTTP 재검사라고 한다.
클라이언트가 사본을 요청했을 때 충분히 오래된 경우에만 재검사를 진행한다.

### 느린 적중

재검사는 원 서버에 작은 재검사 요청을 보내고, 
콘텐츠가 변경되지 않았다면 `304 Not Modified` 라는 응답을 받는다. 
캐시는 이를 신선하다고 표시한 뒤 클라이언트에 제공하는데 이를 재검사 적중 혹은 느린 적중 이라 한다.
이는 서버로부터 객체 데이터를 받을 필요가 없기 때문에 캐시 적중 보다는 느리나 캐시 부적중 보다는 빠르다.

HTTP는 캐시된 객체를 재확인하기 위해 몇 가지 도구를 제공하며, 가장 많이 사용되는 것은 If-Modified-Since 헤더 이다.
서버에게 보내는 GET 요청에 이 헤더를 추가하면 캐시된 시간 이후에 변경된 경우에만 사본을 보내달라는 의미가 된다.

GET If-Modified-Since 요청이 서버에 도착하는 경우 세가지 상황이 발생할 수 있다.
1. 서버 콘텐츠가 변경되지 않은 경우
2. 서버 콘텐츠가 변경된 경우
3. 객체가 삭제된 경우

재검사 적중

서버 객체가 변경되지 않았다면 `304 Not Modified` 라는 응답을 보낸다.
